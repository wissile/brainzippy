# COPPA / children's privacy checklist — DRAFT

> **DRAFT — NOT LEGAL ADVICE.** An engineering checklist mapping what BrainZippy does to the obligations counsel must confirm under the US Children's Online Privacy Protection Act (COPPA Rule, 16 CFR Part 312, as amended in 2025) and related regimes (GDPR/UK GDPR Art. 8, UK Age Appropriate Design Code). **[LAWYER]** marks decisions that only a lawyer can make. Status reflects the code on branch `p1-accounts` (2026-11-18).

## 1. Scope
- [x] Site is directed to children under 13 (ages 3–14) → COPPA applies to any personal information collected from children.
- [x] Guest play collects no personal information server-side (child name, monster, progress stay in localStorage; guest server sync is OFF, D-011).
- [ ] **[LAWYER]** Confirm the server-minted guest UUID API (currently unused by the client) and Cloudflare's IP processing fall under "support for internal operations".

## 2. What the account system collects (engineering facts)
| Item | From whom | Notes |
|---|---|---|
| Parent email | Parent, behind a parent gate | Online contact info of an adult |
| Consent record (wording version, time) | Parent | Wording carried over from onboarding (`src/account/consent.ts`) |
| Monster name, monster design, age band | Parent (dashboard) or the device the child plays on | A monster name could be a real name if a family types one; UI says to use a monster name |
| Optional nickname | Parent only, opt-in, default off | Treat as personal information |
| Progress & round history | Generated by the child's play on a parent-linked device | Persistent identifier (child id) linked to an adult account |
| Friend links, challenge scores | Parents approve both sides | Visible to the other family: monster name, art, weekly points, challenge score |

## 4. Verifiable parental consent (VPC) — **main open decision**
- [x] Current method: parent enters their email behind a parent gate, ticks consent, and confirms via a single-use 15-minute link ("email plus" style). No child data is collected before the parent confirms (profiles are created only after sign-in).
- [ ] **[LAWYER] Is email confirmation sufficient?** Under COPPA, "email plus" is permitted only when information is used **internally** and **not disclosed**. Questions:
  1. Is showing a child's monster name, monster art and points to an approved friend's parent/child a **disclosure** (making personal information publicly or otherwise available)? If yes, a stronger VPC method is required **before friends/challenges are enabled**, e.g. a card transaction (Stripe, planned for billing), signed consent form, video/ID check, or knowledge-based questions.
  2. Is a monster name "personal information" (it may be a real name)? If yes, consider restricting friend-visible names to a generated name list.
  3. Is the daily digest email (to the parent) an internal use? (We believe yes.)
- [x] **Feature flag (engineering, 2026-11-18):** friends, leaderboard and challenges sit behind `FRIENDS_ENABLED` (`wrangler.jsonc`): `"false"` at the top level and in **production**, `"true"` only in staging and local development. While false, every friends/leaderboard/challenge API answers 404 and the parent dashboard hides those sections.
- [ ] **[LAWYER — blocker before `FRIENDS_ENABLED="true"` in production]** Decide whether email-plus is enough or which verifiable-parental-consent method social features need (question 1 above). Do not switch the flag on in production until this is answered in writing.
- [ ] Engineering options ready if counsel requires stronger VPC for social features: gate friends/challenges behind the Stripe card check that billing adds (`worker/lib/entitlements.ts` seam), and keep email-plus for dashboard-only accounts.
- [ ] **[LAWYER — open]** Daily-reminder push subscriptions: we store the browser's push endpoint URL + keys, the chosen local hour and the IANA timezone per device (`migrations/0004_push.sql`; no names, emails or IPs; the parent turns it on behind the parent gate). Is the endpoint (a unique, persistent value) or endpoint + timezone a **persistent identifier** under the COPPA Rule? If so, is this use "support for internal operations" (sending the reminder the parent asked for) and are notice/consent sufficient? Until answered, reminders stay off in production because `VAPID_PUBLIC_KEY` is empty there.
- [ ] **[LAWYER]** Separate consent for disclosure to third parties (2025 amendment) — we disclose to no third parties beyond processors; confirm.

## 5. Parental rights
- [x] Review: parent dashboard shows everything stored per child.
- [x] Export: `GET /api/me/export` (JSON download).
- [x] Delete child profile / delete account: immediate hard delete in D1 (all linked rows).
- [x] Refuse further collection: unlink the device ("Stop saving this device"), delete profile, or never link.
- [x] Revoke friend connections at any time; either parent can remove.
- [ ] **[LAWYER]** Process and identity checks for requests made by email rather than in the signed-in parent area.

## 6. Data minimisation and retention
- [x] No child email, password, photo, voice, location, contacts, birthdate. Age is a coarse band.
- [x] Nickname off by default; never shown to friends.
- [x] Retention schedule implemented by the daily purge cron (`worker/jobs/purge.ts`) and documented in `docs/PRIVACY_SECURITY.md`.
- [ ] **[LAWYER]** Written data retention policy (required by the 2025 COPPA amendments) — confirm periods, including inactive accounts (proposed 24 months) and the up-to-30-day database recovery window (D1 Time Travel).

## 7. Security program
- [x] Hashed tokens and sessions, HttpOnly/Secure/SameSite cookies, Origin checks, rate limits, parameterised SQL, strict validation, no PII in logs (details: `docs/PRIVACY_SECURITY.md`).
- [ ] **[LAWYER]** Written information security program (2025 amendment): designated owner, annual risk assessment, vendor oversight.
- [ ] Independent security review of `worker/**` and `src/account/**` before enabling accounts in production.

## 8. Third parties / processors
- [ ] **[LAWYER]** DPAs and COPPA-appropriate terms with Cloudflare (hosting, D1) and Resend (email).
- [x] No advertising, analytics or tracking SDKs; no third-party scripts or fonts on child pages.

## 9. Child-facing design
- [x] Parent gate (2-digit × 1-digit multiplication) in front of the parent area, sign-up and anything about accounts or money. **[LAWYER]** acceptable as a neutral age screen / speed bump only; not used as consent.
- [x] No chat, no free text between users, no public profiles; sharing uses fixed, authored text.
- [x] Leaderboards are friends-only and weekly; mistakes never cost points.
- [ ] UK AADC: complete a DPIA; confirm defaults (social features off until a parent acts — currently true).

2. Production secrets set (`RESEND_API_KEY`, `SIGNING_SECRET`), sending domain verified in Resend (SPF/DKIM).
3. Remote migration `0003_accounts.sql` applied to staging, tested, then production (owner approval).
4. Security review findings resolved.
